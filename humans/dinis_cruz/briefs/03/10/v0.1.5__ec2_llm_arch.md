# Ephemeral EC2 LLM Architecture
**MGraph-AI Deploy Service · Architect Review**  
Version v0.1.5 · 10 March 2026 · SGraph Send Team

---

## 1. Purpose and Context

The QA team needs LLM inference during CI pipeline execution. The specific use case is detecting issues that pixel-diff cannot catch: untranslated strings in locale pages, text overflow caused by long translated strings (German is notorious for 3× the English length), layout collapse, missing locale switcher elements.

External LLM APIs are ruled out — cost is secondary; the primary driver is building a reusable, owned capability for ephemeral compute with LLM inference. This same pattern will serve customer deployments, other internal workflows, and future CI workloads.

> **Decision recorded:** Build ephemeral EC2 + Ollama pattern inside `MGraph-AI__Service__Deploy`, using the `osbot_aws` EC2 and SSH helper classes. SSH tunnel via port 22 only. Gemma3:4b as the first model. Graviton3 arm64 instances. Spot with on-demand fallback. Region: eu-west-2 only.

## 2. The OSBot Helper Classes

This section describes the existing infrastructure we build on. Understanding these classes is essential — they define the patterns our new Operation class follows.

### 2.1 `EC2` — The AWS API Layer

`EC2` (`osbot_aws.aws.ec2.EC2`) is a `Type_Safe` wrapper over the boto3 EC2 client. It handles all the low-level AWS API calls and exposes clean, typed methods. Key methods we use:

| Method | What it does for us |
|---|---|
| `key_pair_create_to_file(key_name, target_folder)` | Creates EC2 key pair, writes `.pem` to disk, sets `chmod 400`. Returns `path_key_pair` + `key_pair_id`. This is our ephemeral key workflow. |
| `key_pair_delete(key_pair_id)` | Deletes the key pair from AWS after the run. Called in `finally` block. |
| `security_group_authorize_ingress(sg_id, port, cidr_ip)` | Adds an ingress rule. We add port 22 scoped to the runner IP only (`{runner_ip}/32`). |
| `security_group_revoke_ingress(sg_id, port, cidr_ip)` | Removes the ingress rule. Called in `finally` block. |
| `instance_create(..., spot_instance=True)` | Launches a Spot instance with our pre-baked AMI, key name, security group, tags. |
| `instance_terminate(instance_id)` | Terminates the instance. Always called in `finally` block. |
| `wait_for_instance_running(instance_id)` | Blocks until instance enters `running` state. Uses AWS waiters with configurable delay/attempts. |

### 2.2 `EC2_Instance` — Instance Lifecycle

`EC2_Instance` (`osbot_aws.aws.ec2.EC2_Instance`) is a higher-level wrapper that holds instance state and exposes lifecycle operations plus SSH bootstrap. It is the primary object we interact with.

```python
ec2_instance = EC2_Instance()
ec2_instance.create_kwargs = dict(
    image_id          = AMI_ID,
    instance_type     = 'c7g.xlarge',
    key_name          = key_name,
    security_group_id = sg_id,
    spot_instance     = True,
    tags              = {'Purpose': 'sgraph-qa-llm', 'RunId': run_id}
)
instance_id = ec2_instance.create(instance_name=f'sgraph-qa-llm-{run_id}')

# Wait until SSH is accepting connections — this IS our readiness signal
ec2_instance.wait_for_ssh()   # polls is_port_open(ip, 22)

# Bootstrap SSH object
ssh = ec2_instance.ssh(ssh_key_file=key_path, ssh_key_user='ubuntu')
```

`wait_for_ssh()` polls `is_port_open(ip, 22)`. When port 22 accepts connections, our pre-baked AMI guarantees Ollama is already running (systemd started it before sshd became available). This eliminates a separate Ollama health check.

### 2.3 `SSH` — The Remote Execution Facade

`SSH` (`osbot_utils.helpers.ssh.SSH`) is a `Type_Safe` facade that composes all SSH capabilities. It is what `EC2_Instance.ssh()` returns, and what we call throughout the operation.

| SSH method / property | What we use it for |
|---|---|
| `ssh.exec(command)` | Run any shell command. Returns stdout. Used for Ollama warm-up check, service status, one-off queries. |
| `ssh.ssh_linux()` | Returns `SSH__Linux` instance for higher-level Linux operations. |
| `ssh.scp()` | Returns `SCP` instance. Used to upload check scripts and download result files. |
| `ssh.ssh_python()` | Execute Python code or functions remotely. Used to run structured QA check scripts on the instance. |
| `ssh.ssh_execute()` | Returns the underlying `SSH__Execute` with `execute_ssh_args()` — we extend this for tunnel support. |

### 2.4 `SSH__Execute` — Subprocess SSH Wrapper

`SSH__Execute` is the core of all SSH operations. It builds `ssh` arguments and invokes the system `ssh` binary via `subprocess.run` (blocking). Key internals:

```python
def execute_ssh_args(self):   # builds: -p 22 -o StrictHostKeyChecking=no -i keyfile
    ssh_args = []
    if self.ssh_port:              ssh_args += ['-p', str(self.ssh_port)]
    if not self.strict_host_check: ssh_args += ['-o', 'StrictHostKeyChecking=no']
    if self.ssh_key_file:          ssh_args += ['-i', self.ssh_key_file]
    return ssh_args

def execute_command(self, command):
    ssh_args = self.execute_command_args(command)  # adds host + command
    result   = start_process('ssh', ssh_args)      # subprocess.run — BLOCKING
    return result  # { stdout, stderr, status, duration }
```

### 2.5 `SSH__Linux` — Linux Command Helpers

`SSH__Linux` wraps `SSH__Execute` with idiomatic Linux commands. We use it for Ollama service verification.

```python
ssh.ssh_linux().running_processes()          # ps aux — verify ollama is in process list
ssh.ssh_linux().cat('/var/log/ollama.log')   # inspect Ollama startup logs if needed
ssh.ssh_linux().which('ollama')              # confirm ollama binary is on PATH
```

### 2.6 `SCP` — File Transfer

`SCP` extends `SSH__Execute` with `copy_file_to_host()` and `copy_file_from_host()`. Used in the Mitmproxy reference implementation for provisioning service files, and in our workflow for uploading batch check scripts and downloading results.

```python
ssh.scp().copy_file_to_host(local_file='/tmp/qa_checks.json', host_file='.')
ssh.scp().copy_file_from_host(host_file='qa_results.json', local_file='/tmp/qa_results.json')
```

### 2.7 The Gap: SSH Port Forwarding

Port forwarding is explicitly noted as a TODO in `SSH__Linux`:

```python
# if port_forward:      # todo: add support for port forward (this will need async execution)
#     local_port  = port_forward.get('local_port' )
#     remote_ip   = port_forward.get('remote_ip'  )
#     remote_port = port_forward.get('remote_port')
```

The existing `execute_command()` uses `subprocess.run` — blocking. Port forwarding requires `subprocess.Popen` — non-blocking, long-running process. We add `start_port_forward()` to `SSH__Execute`:

```python
def start_port_forward(self, local_port: int, remote_port: int,
                       remote_host: str = '127.0.0.1') -> subprocess.Popen:
    """Start SSH tunnel in background. Caller must terminate the process."""
    ssh_args  = self.execute_ssh_args()          # reuse existing arg builder
    ssh_args += ['-N']                           # no command, tunnel only
    ssh_args += ['-L', f'{local_port}:{remote_host}:{remote_port}']
    ssh_args += [self.execute_command_target_host()]
    return subprocess.Popen(['ssh'] + ssh_args)  # non-blocking

# Usage:
tunnel = ssh.ssh_execute().start_port_forward(local_port=11435, remote_port=11434)
# ... all Ollama HTTP calls go to localhost:11435 ...
tunnel.terminate()
```

This is the **only change required to existing classes**. Everything else is new code.

> **Why a tunnel instead of SSH exec per Ollama call?** For batch QA checks (10–50 per CI run), opening a new subprocess per call adds ~80ms overhead each. The tunnel opens once, all HTTP calls go through it at near-local latency.

## 3. Secure Communication Model

Ollama's default config binds to `127.0.0.1:11434` — localhost only. We never change that. The SSH tunnel is the security layer.

```
GitHub Actions runner
    │
    │  SSH tunnel (port 22 only — the only open port on the security group)
    │  ssh -N -L 11435:127.0.0.1:11434 ubuntu@{ec2-ip}
    │
    ▼
EC2 instance
    └── Ollama listening on 127.0.0.1:11434 (never exposed publicly)

CI runner talks to localhost:11435 as if Ollama were local.
Ollama never touches a public interface.
```

### Ephemeral Key Pair

We use `EC2.key_pair_create_to_file()` to generate a fresh key pair per instance launch. No stored SSH keys in GitHub Secrets.

```
Deploy Service receives /workflows/execute
    │
    ├─ EC2.key_pair_create_to_file(key_name=f'sgraph-qa-{run_id}')
    │     → writes {run_id}.pem to /tmp, sets chmod 400
    │     → key_pair_id stored for cleanup
    │
    ├─ instance launched with that key_name
    │
    ├─ SSH connects using the .pem file
    │
    └─ finally:
          EC2.key_pair_delete(key_pair_id=key_pair_id)
          os.unlink('/tmp/{run_id}.pem')
```

The private key exists only on the Deploy Service runner's filesystem for the duration of the run. Nothing to rotate, nothing stored in Secrets Manager.

### Security Group Management

We use a **single stable, pre-created SG** (`sgraph-qa-llm-sg`) with no inbound rules by default. Creating a new SG per run would add provisioning delay and risk hitting AWS SG creation rate limits under concurrent CI runs.

The per-run lifecycle is:

```
Launch:   security_group_authorize_ingress(sg_id, port=22, cidr_ip=f'{runner_ip}/32')
Cleanup:  security_group_revoke_ingress(sg_id,    port=22, cidr_ip=f'{runner_ip}/32')
```

The SG itself is never deleted. The rule is scoped to the specific runner IP for that run, so concurrent runs each add and remove their own rule independently without conflict.

## 4. Full Execution Flow

```
Deploy Service receives POST /workflows/execute
│
├─ 1. Create ephemeral key pair
│       EC2.key_pair_create_to_file(key_name=f'sgraph-qa-{run_id}', target_folder='/tmp')
│       → path_key_pair, key_pair_id
│
├─ 2. Add temporary security group rule
│       EC2.security_group_authorize_ingress(sg_id, port=22, cidr_ip=f'{runner_ip}/32')
│
├─ 3. Launch EC2_Instance (Spot)
│       ec2_instance.create_kwargs = {
│           image_id, instance_type='c7g.xlarge',
│           key_name, security_group_id,
│           spot_instance=True,
│           tags={'RunId': run_id, 'Purpose': 'sgraph-qa-llm'}
│       }
│       instance_id = ec2_instance.create()
│
├─ 4. Wait for SSH readiness  ← this IS the readiness signal
│       ec2_instance.wait_for_ssh()   # polls port 22
│       Port 22 open = kernel up + sshd ready + Ollama already running (systemd)
│
├─ 5. Bootstrap SSH
│       ssh = ec2_instance.ssh(ssh_key_file=path_key_pair, ssh_key_user='ubuntu')
│
├─ 6. Optional: verify Ollama is alive
│       ssh.exec('curl -s http://127.0.0.1:11434/api/tags')
│
├─ 7. Open SSH tunnel
│       tunnel = ssh.ssh_execute().start_port_forward(
│           local_port=11435, remote_port=11434)
│
├─ 8. Run batch QA checks via localhost:11435
│       results = batch_invoke(checks, ollama_url='http://localhost:11435')
│
└─ finally (always runs — even when raising)
        tunnel.terminate()
        EC2.instance_terminate(instance_id)
        EC2.key_pair_delete(key_pair_id=key_pair_id)
        EC2.security_group_revoke_ingress(sg_id, port=22, cidr_ip=f'{runner_ip}/32')
        os.unlink(path_key_pair)
```

`Mitmproxy__Create__EC2_Instance` (from the existing codebase) is the direct template for our Operation class. The structural parallels are exact:

| `Mitmproxy__Create__EC2_Instance` | `Operation__EC2__Ephemeral__LLM` |

## 5. Failure Handling

**Every failure breaks the CI pipeline with a clear error.** There are no silent failures, no partial results, no retries. At this stage of the capability we want full visibility into every EC2 or Spot failure.

```python
try:
    self._launch()
    self._open_tunnel()
    results = self._batch_invoke(self.checks)
    return Schema__Response__EC2__LLM__Execute(success=True, results=results, ...)

except SpotFulfillmentError as e:
    raise CIBreakingError(f"EC2 Spot not fulfilled: {e}")

except SSHTimeoutError as e:
    raise CIBreakingError(f"EC2 launched but SSH never became available: {e}")

except OllamaError as e:
    raise CIBreakingError(f"Ollama unresponsive on instance {self.instance_id}: {e}")

except SpotInterruptionError as e:
    raise CIBreakingError(f"EC2 Spot interrupted mid-run on instance {self.instance_id}")

finally:
    self._cleanup()  # always runs — even when raising
```

The `finally` block always executes, so we never leak instances, key pairs, or open security group rules regardless of which exception was raised. The error message in each case names the failure mode clearly so CI logs are immediately actionable.

## 6. The Type__Twin (Surrogate for Tests)

Following the GitHub Surrogate pattern established in Phase 1, we build an in-memory twin of the Ollama HTTP API. All unit tests use this twin — no EC2 instances are launched.

```python
class Ollama__Surrogate(Type_Safe):
    """In-memory twin of Ollama's HTTP API. Deterministic responses for known prompts."""
    responses  : dict = {}   # prompt_hash → canned JSON response
    latency_ms : int  = 50   # simulated inference time
    calls_made : list = []   # for assertion in tests

    def api_chat(self, model: str, messages: list) -> dict:
        prompt_hash = hash(str(messages))
        if prompt_hash in self.responses:
            return self.responses[prompt_hash]
        raise ValueError(f'Unknown prompt — add to surrogate: {messages[0]["content"][:80]}')


# Test pattern (mirrors GitHub surrogate tests exactly):
class test_Operation__EC2__LLM(unittest.TestCase):
    @classmethod
    def setUpClass(cls):
        cls.surrogate = Ollama__Surrogate()
        cls.surrogate.responses[hash(str(KNOWN_PROMPT))] = {
            'findings': [], 'passed': True
        }
        cls.operation = Operation__EC2__Ephemeral__LLM(
            ollama_client = cls.surrogate   # injected — no real EC2
        )
```

Same confidence properties as the GitHub surrogate: all production code paths execute, only the external boundary (EC2 + Ollama) is replaced. Tests run in-memory in < 100ms with no AWS credentials required.

## 7. Pre-Baked AMI — The Performance Lever

Boot time is dominated by model loading, not hardware init. Pre-baking eliminates model download entirely. This is the k8s equivalent of a warmed node with the image already cached.

### AMI Build Steps

```bash
# 1. Launch base Ubuntu 22.04 arm64 instance (c7g.xlarge) in eu-west-2

# 2. Install Ollama
curl -fsSL https://ollama.com/install.sh | sh

# 3. Pull model (weights written to /var/lib/ollama/models/)
ollama pull gemma3:4b

# 4. Configure Ollama to bind localhost only on boot
# /etc/systemd/system/ollama.service.d/override.conf
[Service]
Environment='OLLAMA_HOST=127.0.0.1:11434'   # SSH tunnel provides access

# 5. Verify model loads cleanly
ollama run gemma3:4b 'respond with the word OK only'

# 6. Bake AMI using EC2.create_image()
ami_id = ec2.create_image(instance_id=instance_id, name='sgraph-qa-llm-gemma3-4b-v1')

# 7. Store AMI ID as GitHub Secret: QA_LLM_AMI_ID
```

### AMI Naming Convention

One AMI per model. When a new model is introduced, a new AMI is built — no shared AMIs with multiple models pulled.

```
sgraph-qa-llm-{model-name}-v{build}

Examples:
  sgraph-qa-llm-gemma3-4b-v1
  sgraph-qa-llm-phi4-mini-v1
  sgraph-qa-llm-llama3-2-3b-v1
```

Config maps model name → AMI ID. Adding a new model = one build + one config entry.

### Expected Boot-to-First-Token Timing

| Phase | Duration (est.) | Notes |
|---|---|---|
| EC2 Spot fulfillment | 2–5 s | Graviton3 availability is high in eu-west-2 |
| Kernel + userdata boot | 10–18 s | Nitro hypervisor, no model download |
| systemd starts `ollama.service` | 3–6 s | Loads model weights from local disk |
| SSH port 22 accepts | **~25–35 s total** | This is our readiness signal |
| Tunnel open + first token | < 1 s | Tunnel opens instantly; model already hot |
| **Total: launch → first token** | **~30–45 s** | Target for pre-baked AMI |

## 8. Schema Design (Type_Safe)

Following the same patterns established for GitHub Secrets schemas in Phase 1:

```python
class Schema__QA__Check(Type_Safe):
    check_id        : str        # unique ID for this check
    prompt          : str        # full prompt sent to Ollama
    expected_schema : dict = {}  # JSON schema the model must return

class Schema__QA__Result(Type_Safe):
    check_id        : str
    passed          : bool
    findings        : list  = []   # list of issue strings
    raw_response    : str   = ''   # full model output for debugging
    tokens_per_sec  : float = 0.0  # for performance tracking
    duration_ms     : int   = 0

class Schema__Request__EC2__LLM__Execute(Type_Safe):
    ami_id          : str
    instance_type   : str  = 'c7g.xlarge'
    spot_instance   : bool = True
    runner_ip       : str          # injected by CI, scopes security group rule
    model           : str  = 'gemma3:4b'
    checks          : list = []    # List[Schema__QA__Check]

class Schema__Response__EC2__LLM__Execute(Type_Safe):
    success           : bool
    instance_id       : str   = ''
    instance_type     : str   = ''
    spot_fulfilled    : bool  = False
    boot_time_seconds : float = 0.0
    results           : list  = []   # List[Schema__QA__Result]
    total_duration_ms : int   = 0
    error             : str   = ''
```
