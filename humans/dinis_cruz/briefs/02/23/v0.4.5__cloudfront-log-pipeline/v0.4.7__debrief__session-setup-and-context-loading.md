### Gap 3: Type_Safe Framework Documentation (6 documents)

**What I learned that wasn't in the briefing pack:**

From **Type_Safe core guide:**
- Ban on raw primitives (`str`, `int`, `float`) — must use Safe_* types
- Schemas must be pure data containers (NO methods)
- Simplified default value assignment (auto-conversion handles it)
- Reserved method names (`json`, `from_json`, `obj`, `reset`, `print`)
- `None` return is always valid — no need for `Optional[T]`
- No `str()` casts — Type_Safe handles conversions
- No exceptions for missing resources — return `None`

From **Python formatting guide:**
- `═══` file headers before imports
- NO docstrings ever — inline comments only
- Aligned imports at consistent column
- Multi-param method vertical alignment rules
- No underscore prefix on helper methods
- No line break before first parameter
- Explicit `is True` / `is False` for booleans

From **Safe primitives reference:**
- 100+ domain-specific types available (HTTP, LLM, crypto, git, files, identifiers, numerical, web)
- Custom Safe type creation patterns
- Which Safe type to choose for each use case

From **Testing guidance:**
- Context manager pattern with `_` (`with Schema__X() as _:`)
- `.obj()` + `__` class for single-assertion state verification
- `__SKIP__` for dynamic values, `.contains()` for partial matching
- `setUpClass` vs `setUp` — 10-100x performance difference
- Bug documentation pattern (tests that pass with buggy behaviour)
- Error message testing with `re.escape()`

From **Collections subclassing guide:**
- `Dict__`, `List__`, `Set__` naming prefixes
- Pure type definitions only (no methods in collection subclasses)
- Auto-conversion from plain dicts/lists
- Operations (`copy`, `|`, `fromkeys`) preserve subclass type

From **Decorator guide:**
- `@type_safe` two-phase validation (call-time + return-time)
- Auto-conversion of return values to Type_Safe collections
- `List[T]` validates every element, not just the list
- `Union` for multi-type params, `Type[T]` for class params

**Recommendation:** This is the biggest gap. Include at minimum the Type_Safe core guide and the formatting guide in every dev pack. For sessions that will write tests, include the testing guidance too. Consider creating a condensed "Type_Safe essentials" document for dev packs.

## What I Learned

### Architecture Understanding (from briefing pack)

1. **LETS Pipeline** is a 4-step pattern (Load → Extract → Transform → Store) applied to CloudFront real-time logs. Each step reads from cache, processes, writes to cache with a different namespace prefix.

2. **Finality Cascade** is the key innovation for temporal aggregation — a period is "final" only when ALL source periods are final, cascading from 30min → hourly → daily → monthly. This prevents incorrect rollups from incomplete data.

3. **Cache Namespace Strategy** uses separate namespaces (`sa-cloudfront-raw/`, `sa-cloudfront-consolidated/`, `sa-cloudfront-aggregate/`) rather than sub-paths, with specific key structures for each level.

4. **Privacy-by-Design** means `c-ip` is excluded at the CloudFront config level (not stripped after collection). Tests must verify no IP patterns exist in parsed output.

5. **Decision D050** carves out a boto3 exception for collector classes with lazy imports — this is the established pattern that `CloudFront__Logs__Collector` already follows.

### Codebase Patterns (from GitHub Digest + code-context.md)

6. **Type_Safe everywhere** — no Pydantic, no raw dicts for structured data. Schemas are pure data containers (no methods). Services contain business logic.

7. **No mocks, no patches** — tests use real implementations with in-memory backends. Full stack starts in ~100ms. LocalStack is the only acceptable "fake" (for S3).

8. **Formatting is structural** — vertical alignment, `═══` headers, inline comments (never docstrings), no underscore prefixes, explicit `is True`/`is False`. This isn't cosmetic; it enables visual pattern recognition for bug detection.

9. **Ban on raw primitives** is a security and correctness rule. Every `str`, `int`, `float` should be a domain-specific Safe type. This catches SQL injection, XSS, overflow, and precision bugs at assignment time.

10. **Explorer team rules** (from CLAUDE.md): build first versions, move fast, capture learnings. Don't deploy to production. Don't optimise for performance. That's Villager territory.

### Testing Philosophy (from Type_Safe testing guidance + CLAUDE.md)

11. **Context manager with `_`** is the standard pattern — `with Schema__X() as _:` for every Type_Safe test.

12. **`.obj()` + `__` class** enables single-assertion verification of complete object state, with `__SKIP__` for dynamic values and `.contains()` for partial matching.

13. **`setUpClass`** for anything >100ms — the math is compelling (20 tests × 5s setup = 100s with setUp vs 5s with setUpClass).

14. **Bug tests that pass** document current behaviour, prevent accidental "fixing", and automatically become regression tests when the bug is fixed.
