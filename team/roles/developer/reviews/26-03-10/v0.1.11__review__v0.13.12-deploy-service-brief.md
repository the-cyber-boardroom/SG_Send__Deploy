## a) Assessment of the Brief

### What is practical and well-defined

1. **The Router Lambda state machine** is crisply specified. Three states (RUNNING, STOPPED, STARTING), three responses (307 redirect, start+waiting page, waiting page). This is immediately implementable. The vault file schema at `vault://deploy/instances/deploy-001.json` gives us a concrete data contract.

2. **The auto-shutdown dual mechanism** (EC2 heartbeat + EventBridge watchdog) is well thought through. The heartbeat is a FastAPI background task writing `last_seen` to vault; the watchdog is a separate Lambda on a schedule. Both are small, self-contained pieces. The 25-minute maximum zombie lifetime (15 min idle + 10 min watchdog window) is a clear budget bound.

3. **The async job model** is well-defined from an API contract perspective: POST returns 202 with `job_id`, GET `/jobs/{id}` returns status/step/log. This is a standard pattern and maps cleanly to a background thread or asyncio task on the EC2.

4. **Phase 1 scope** is tight and achievable. It only requires: Router Lambda (vault read, EC2 start/describe, waiting page, /status, redirect), EC2 heartbeat/idle-shutdown, and the EventBridge watchdog. No DNS, no SSH stack creation, no CLI. This is the right first cut.

5. **The EC2 security boundary** is clear. Deploy EC2 holds high-privilege IAM creds and SSH keys; Lambda holds only start/stop/describe EC2. The brief explicitly states what Lambda can and cannot do.

6. **The Type__Twins default-mode concept** aligns with the existing `EC2_Provider` / `EC2_Provider__Twin` abstraction already in the codebase. The brief's vision of "Twin as default, real AWS as graduation" is an extension of what we already have.

### What needs more detail before coding can start

1. **Vault client API.** The brief references `vault.write()`, `vault.read()`, `vault://deploy/instances/deploy-001.json` but does not specify the Python API for interacting with the SG/Send vault. Questions:
   - What library/class do we import? Is there an existing `osbot-*` vault client, or do we build one?
   - How does authentication work? The brief says "vault write key in Lambda env vars and on EC2." What is the API shape: `Vault(write_key=...).read('deploy/instances/deploy-001.json')`?
   - Is the vault an HTTP API (to a running SG/Send instance), an S3 backend, or something else?
   - For Type__Twins mode, do we need a `Vault__Twin` that stores in-memory?

   This is the single biggest blocking dependency for Phase 1. Everything reads/writes vault state.

2. **Waiting page HTML.** The brief shows a mockup but does not specify:
   - Where does the HTML template live? Inline in the Lambda handler, or a static file?
   - Does it need SG/Send branding, or is a minimal page acceptable for Phase 1?
   - The JS poller hits `/status` on the Router Lambda. This means the Lambda needs to handle at least two routes: the root (waiting page or redirect) and `/status` (JSON status response). Is this via API Gateway path routing?

3. **EC2 FastAPI port.** The brief says `http://{ip}:8080` for the redirect. The current CLAUDE.md says port 443 inbound only. This needs reconciliation. For Phase 1 with raw IP (no TLS), port 8080 makes sense, but this contradicts Rule 8 in the current project rules.

4. **Deploy EC2 AMI.** Phase 1 assumes a pre-baked AMI exists with the Deploy Service FastAPI already installed. The brief describes the AMI baking process (ENV4/CI) but that is not Phase 1. For Phase 1, do we manually bake a first AMI, or do we boot from a base Ubuntu AMI and install at startup (slow)?

5. **Lambda deployment mechanism.** The current codebase deploys the Lambda via `Deploy__Service` which extends `Deploy__Serverless__Fast_API` and packages the full FastAPI app + UI into a Lambda zip. The new Router Lambda is fundamentally different: it is thin, has no FastAPI, no SSH, no UI. Do we:
   - Create a separate Lambda function alongside the existing one?
   - Replace the existing Lambda?
   - Use a simple Python handler without any framework?

6. **The `/stacks` API contract.** The brief lists endpoints (`/stacks`, `/stacks/{id}/ssh`, etc.) but does not define request/response schemas. Before Phase 3 coding, we need:
   - `Schema__Stack__Create__Request` (type, instance_type, config)
   - `Schema__Stack` (id, type, status, endpoint, instance_id, created_at)
   - `Schema__Job` (job_id, status, step, total_steps, log[], result)

7. **CLI entry point.** The brief says `sg-deploy` CLI via pip install. The current `pyproject.toml` has no `[tool.poetry.scripts]` section. This needs a `console_scripts` entry point and a CLI module. Not Phase 1, but needs design.

### Developer concerns

1. **Dependency on vault client is critical-path.** Without a vault read/write client, Phase 1 cannot start. I would recommend stubbing this with a simple S3 or local-file implementation first, then migrating to the real SG/Send vault.

2. **Two Lambda functions, not one.** The brief implies we need at minimum two Lambda functions: Router Lambda (permanent, thin) and Watchdog Lambda (EventBridge-triggered). The current infrastructure deploys a single Lambda. We need to think about how these are deployed and managed.

3. **Testing the Router Lambda.** The Router Lambda contains a state machine (read vault, decide action, respond). This should be testable purely in-memory with a `Vault__Twin`. The brief's Type__Twins emphasis supports this, but we need the vault twin abstraction defined.

4. **The brief mentions boto3 directly** in several places ("Has boto3 + Type_Safe / Type_Twins AWS wrappers"). CLAUDE.md Rule 2 says "Never use boto3 directly." The brief's intent seems to be that the Deploy EC2 uses `osbot-aws` wrappers (which use boto3 internally), but the EC2 instance itself may need direct boto3 for operations not yet wrapped in osbot-aws (like `create_image`, `create_target_group`). This tension needs resolution.

## c) Implementation Roadmap

### Phase 1: Boot-on-demand with IP redirect

The critical path is: vault client -> vault state schema -> Router Lambda state machine -> Router Lambda handler -> EC2 heartbeat -> Watchdog Lambda.

The `Schema__Vault__Instance` is a Type_Safe class:

class Schema__Vault__Instance(Type_Safe):
    status       : str   = 'stopped'    # stopped | starting | running | stopping
    instance_id  : str   = ''

    dns          : str   = ''

The `Vault__Client` interface needs: `read_instance(name: str) -> Schema__Vault__Instance` and `write_instance(name: str, state: Schema__Vault__Instance) -> bool`.

EC2 start/describe calls go through `osbot-aws` EC2 wrapper (not the existing `EC2_Provider` abstraction -- the Router Lambda needs minimal EC2 calls, not the full provider).

The waiting page HTML should be inline in the handler or a single file loaded at import time (Lambda cold start). The JS poller:
```javascript
setInterval(async () => {
    const r = await fetch('/status');
    const d = await r.json();
    if (d.status === 'ready') window.location = d.endpoint;
    updateUI(d);
}, 3000);
```

#### Task 4: EC2 heartbeat and idle shutdown
**Files:**
- Create `sg_send_deploy/ec2/actions/Heartbeat__EC2.py`
- Modify `sg_send_deploy/lambda__deploy/Fast_API__SG_Send__Deploy.py` (add middleware for `last_request_at`, add startup background task)
- Create `tests/unit/ec2/test__Heartbeat__EC2.py`

**Complexity:** M
**Unblocks:** The "shuts down when idle" acceptance criterion.
**Depends on:** Task 1.

The heartbeat is a background asyncio task registered on FastAPI startup:
```python
async def heartbeat_loop(vault_client, instance_name, idle_timeout):
    last_request_at = time.time()
    while True:
        await asyncio.sleep(60)
        vault_client.write_instance(instance_name, 
            Schema__Vault__Instance(last_seen=datetime.now(timezone.utc).isoformat(), ...))
        if time.time() - last_request_at > idle_timeout:
            vault_client.write_instance(instance_name, 
                Schema__Vault__Instance(status='stopping', ...))
            subprocess.run(["sudo", "shutdown", "-h", "now"])
```

FastAPI middleware updates `last_request_at` on every request.

#### Task 5: Watchdog Lambda
**Files:**

**Complexity:** S
**Unblocks:** Belt mechanism for cost safety.
**Depends on:** Task 1.

Simple EventBridge-triggered handler: read vault state for all known instances, check `last_seen` age, stop any instance where `now - last_seen > idle_timeout + 600` (10 min buffer). Uses `osbot-aws` EC2 for `stop_instances`.

### Phase 1 Critical Path

```
Task 1 (Vault) ──> Task 2 (State Machine) ──> Task 3 (Router Lambda) ──> Task 9 (Deploy)
      │                                                                        │
      ├──> Task 4 (Heartbeat) ─────────────────────────────────────────────────┤
      │                                                                        │
      └──> Task 5 (Watchdog) ──────────────────────────────────────────────────┘

Task 6 (Job Model) ──> Task 7 (Stacks Routes) ──> Task 8 (Refactor LLM Op)
```

Tasks 1-5 and Task 9 are the minimum for the "Deploy Appliance boots on demand, shuts down when idle" deliverable. Tasks 6-8 can be built in parallel and are needed for the stacks API but not for the boot-on-demand demo.

### Estimated total for Phase 1
- 9 tasks, approximately 4 S + 5 M complexity
- New files: ~20 production, ~10 test
- Modified files: ~3 (Fast_API__SG_Send__Deploy.py, Deploy__Service.py, pyproject.toml)
- The vault client dependency resolution is the gating item

### Phase 2 and 3 (summary only)

**Phase 2 (DNS):** Add Route53 calls to Router Lambda (on start) and Watchdog Lambda (on stop). Extend `EC2_Provider` with `route53_upsert` and `route53_delete`. Extend vault schema with `dns` field. Modify redirect to use HTTPS hostname. Requires ACM wildcard cert for `*.sgraph.ai`. Complexity: M overall.

**Phase 3 (Appliance management):** Implement `Stack__LLM`, `Stack__Send_Ephemeral` definitions with full SSH provisioning scripts. Each is a sequence of osbot-utils SSH commands run against a target EC2. Add `/stacks/{id}/ssh` route (proxies SSH commands to target instance). Add `/stacks/{id}/logs` (reads remote logs via SSH). This is the bulk of the work and depends heavily on the osbot-utils SSH API maturity. Complexity: L overall.

### Key risk: the vault client

If the SG/Send vault client is not available or its API is not yet stable, I recommend implementing `Vault__Client__S3` as an interim solution. It would store JSON files in an S3 bucket with server-side encryption. This preserves the interface contract (`read_instance` / `write_instance`) and can be swapped for the real vault client later. The Type__Twins in-memory version (`Vault__Client__Twin`) should be built regardless for unit tests.

---

**Summary:** The brief is architecturally sound and the Phase 1 scope is well-bounded. The existing codebase has good abstractions (`EC2_Provider`, `Type__Twin__EC2__Fleet`, `Audit_Trail`) that map directly to the brief's requirements. The main blocking dependency is the vault client. The Router Lambda is a fundamentally different artifact from the current full-fat Lambda handler and should be built as a separate module (`lambda__router/`). The current `Operation__EC2__Ephemeral__LLM` is a prototype of what becomes the generalized async stack creation model. Nine tasks, vault client first, Router Lambda on the critical path.
