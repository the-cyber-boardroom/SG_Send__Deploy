## Executive Summary

The brief proposes ephemeral EC2 + Ollama + SSH port forwarding for QA inference workloads in the CI pipeline. From an implementation standpoint, the architecture is **feasible** -- osbot packages support 90% of requirements. However, **5 concrete blockers** exist that require resolution before execution.

## 2. Critical Findings

### 2.1 BLOCKER #1: `security_group_revoke_ingress()` Missing from osbot-aws (HIGH)

The brief's cleanup flow calls `EC2.security_group_revoke_ingress()` in the `finally` block. This method **does not exist** in osbot-aws v2.39.10.

- The boto3 client has `revoke_security_group_ingress` but `EC2` class doesn't wrap it
- Without revocation, stale ingress rules accumulate on the pre-created SG
- Under sustained CI load, SG rule limit (200 rules per SG) could be hit

**Resolution options:**
1. Contribute `security_group_revoke_ingress()` to osbot-aws upstream (recommended)
2. Use boto3 directly (violates CLAUDE.md rule 2)
3. Implement periodic SG rule cleanup job (tactical fix)
4. Use temporary SGs per run (adds 5-10s provisioning delay)

### 2.2 BLOCKER #2: `c7g.xlarge` Not in Allowed Instance Types (CRITICAL)

Current config (`EC2_Budget_Config.py`):
```python
ALLOWED_INSTANCE_TYPES = ['t3.micro', 't3.small', 't3.medium']
```

The brief requires `c7g.xlarge` (Graviton3, ARM64, 4 vCPU, 16 GB). This is not allowlisted.

**Cost conflict:**
- c7g.xlarge Spot: ~$0.03-0.04/hr (~$7-10/day)
- Daily budget cap: $10.00 (CLAUDE.md rule #14)
- One LLM instance consumes 70-100% of daily budget

**Resolution options:**
1. Separate budget limit for LLM workflows (recommended)
2. Use smaller instance (c7g.medium, ~$0.02/hr Spot)
3. Increase global budget cap
4. Make budget per-instance instead of global

### 2.3 BLOCKER #3: Lambda Has No `ssh` Binary (HIGH)

`SSH__Execute` uses `subprocess.run('ssh', ...)` -- the system ssh binary. **Lambda does not have `/usr/bin/ssh`.**

The brief proposes adding `start_port_forward()` to `SSH__Execute` using `subprocess.Popen(['ssh'] + ssh_args)`. This won't work on Lambda.

**Resolution:** Use paramiko's `Transport.open_channel()` for port forwarding instead of subprocess ssh. This is a **design change** from the brief.

**Critical question:** Does the Deploy Lambda orchestrate the workflow, or does the CI runner call osbot-aws directly?
- If **Lambda** orchestrates -> must use paramiko tunneling
- If **CI runner** orchestrates directly -> system `ssh` works fine, Phase 1 is unblocked as-written

### 2.4 BLOCKER #4: SSH Tunnel Test Strategy Ambiguous (MEDIUM)

When both `EC2_Provider__Twin` and `Ollama__Surrogate` are injected in tests, the SSH tunnel is bypassed entirely. Need a decision:

**Option 1 (Recommended):** Skip SSH tunnel in unit tests via flag
```python
class Operation__EC2__Ephemeral__LLM(Type_Safe):
    use_real_tunnel: bool = True

    def _open_tunnel(self):
        if not self.use_real_tunnel:
            return  # short-circuit for unit tests
```

**Option 2:** Create `SSH__Tunnel__Surrogate` mock (more complex, limited benefit)

### 2.5 BLOCKER #5: Runner IP Source Unclear (MEDIUM)

The brief's `Schema__Request__EC2__LLM__Execute` requires `runner_ip` but doesn't specify the source. Options:
- GitHub Actions `${{ runner.ip }}` (self-hosted runners don't provide this)
- Inferred from HTTP request `request.client.host` (fails behind proxy/NAT)
- Passed in header (spoofable)
- Lambda VPC static IP (no dynamic scoping needed)

## 3. Route Integration

### Proposed Structure

```
sg_send_deploy/
  workflows/                              # NEW MODULE
    routes/Routes__Workflows.py           # POST /workflows/execute
    actions/
      Service__Workflows.py               # Orchestration
      Operation__EC2__Ephemeral__LLM.py   # Execution flow
    schemas/
      Schema__Request__LLM__Execute.py
      Schema__Response__LLM__Execute.py
      Schema__QA__Check.py
      Schema__QA__Result.py
    providers/
      Ollama__Client.py                   # HTTP interface to Ollama
      Ollama__Surrogate.py                # Test twin
```

### Deploy__Fast_API Integration

```python
class Deploy__Fast_API(Serverless__Fast_API):
    service_workflows: Service__Workflows = None

    def setup_routes(self):
        self.add_routes(Routes__Info)
        self.add_routes(Routes__EC2_Instances, ...)
        self.add_routes(Routes__Workflows,                    # NEW
                        service_workflows=self.service_workflows)
```

Pattern is fully compatible with existing route registration.

### Testing Pattern

Twin composition mirrors existing approach:
```python
fleet     = Type__Twin__EC2__Fleet()
provider  = EC2_Provider__Twin(fleet=fleet)
ollama    = Ollama__Surrogate()
operation = Operation__EC2__Ephemeral__LLM(
    ec2_provider    = provider ,
    ollama_client   = ollama   ,
    use_real_tunnel = False    )
```

**3 decisions needed before proceeding:**

| # | Decision | Impact |
