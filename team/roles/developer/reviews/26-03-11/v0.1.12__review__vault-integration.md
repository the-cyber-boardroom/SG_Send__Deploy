## 2. Type_Safe Compatibility -- `_sync` Field

**Status:** BLOCKER

The brief proposes:

```python
class Service__Vault(Type_Safe):
    _sync : object = None  # Vault__Sync instance (not a Type_Safe field)
```

This is problematic. `Type_Safe` (from `osbot-utils`) uses `__init_subclass__` and `__setattr__` hooks to enforce type annotations. Fields prefixed with `_` have specific behavior in Type_Safe:

- Single-underscore attributes (`_sync`) may or may not be tracked by Type_Safe depending on the version. In some versions, `Type_Safe` ignores underscore-prefixed attributes; in others, it treats them as part of the schema.
- The annotation `_sync : object = None` may conflict with Type_Safe's strict typing because `object` is overly broad, and the `None` default might not be accepted as a valid `object` value.

**The existing twin pattern (`EC2_Provider__Twin`, `Type__Twin__EC2__Fleet`) avoids this issue entirely** -- `EC2_Provider__Twin` uses a plain `__init__` method and does NOT extend `Type_Safe`. `Type__Twin__EC2__Fleet` also uses plain `__init__` with `self.instances = {}`.

**Recommended fix:** Either:
1. Do not extend `Type_Safe` for `Service__Vault` (use a plain class like `EC2_Provider__Twin` does), or
2. Use a lazy property pattern instead of `_sync`:

```python
class Service__Vault(Type_Safe):
    vault_key    : str = ''
    access_token : str = ''
    local_dir    : str = ''

    def sync(self) -> Vault__Sync:
        if not hasattr(self, '__vault_sync'):
            api = Vault__API(base_url='', access_token=self.access_token)
            api.setup()
            self.__vault_sync = Vault__Sync(crypto=Vault__Crypto(), api=api)
        return self.__vault_sync
```

Option 2 is preferred -- it keeps Type_Safe for the config fields while avoiding the `_sync` annotation problem. Double-underscore attributes are name-mangled by Python and will not be picked up by Type_Safe's annotation scanner.

## 4. Twin Pattern Match

**Status:** PARTIALLY COMPATIBLE -- different pattern, but acceptable

The existing twin pattern has two variants in this codebase:

**Variant A: Provider Twin** (`EC2_Provider__Twin`)
- Extends `EC2_Provider` (the real provider's base class)
- Uses plain `__init__`, holds a `Type__Twin__EC2__Fleet` internally
- Is a drop-in replacement at the provider layer

**Variant B: Type Twin** (`Type__Twin__EC2__Fleet`, `Type__Twin__EC2__Instance`)
- Uses plain `__init__` or extends `Type_Safe`
- Simulates AWS resource behavior with in-memory state

The proposed `Service__Vault__Twin`:
- Extends `Type_Safe` (like Variant B)
- Is a drop-in replacement for `Service__Vault` (like Variant A)
- Uses `dict` for in-memory file storage
- Has a `seed()` helper method (new pattern, but useful)

**Compatibility concern:** The twin does NOT share a common base class or protocol with `Service__Vault`. The brief relies on duck typing -- both classes have the same method signatures. This works in Python, but the existing twin pattern (Variant A) uses inheritance from a shared base class.

**Recommendation:** Consider creating a base class or Protocol:

```python
class Service__Vault__Base(Type_Safe):
    def is_configured(self) -> bool: ...
    def can_write(self) -> bool: ...
    # etc.
```

This is not a blocker -- duck typing works fine -- but it would improve IDE support and catch interface drift early.

## 6. FastAPI App Wire-up Complexity

**Status:** LOW COMPLEXITY

The current `Fast_API__SG_Send__Deploy` has 4 service fields and a clean `setup()` / `setup_routes()` split. Adding vault requires:

**Changes to `setup()`:**
- Add `service_vault` field declaration (1 line)
- Add vault initialization block before existing service init (5-6 lines)
- Optionally read vault config to populate `EC2_Budget_Config` (3-4 lines)

**Changes to `setup_routes()`:**
- Add one `self.add_routes(Routes__Vault, ...)` call (2 lines)

**Risk:** The brief proposes initializing vault FIRST in `setup()`, then using vault data to configure other services. This changes the initialization order. Currently, services are independent. After this change, `service_instances` depends on vault config. This is a reasonable dependency but needs care -- if vault is in degraded mode, the existing defaults must still work.

The brief handles this correctly: `budget_data = self.service_vault.config_budget()` returns `{}` when not configured, and `EC2_Budget_Config(**budget_data) if budget_data else EC2_Budget_Config()` falls back to defaults.

**Merge complexity:** Low. The file is 92 lines. Changes are additive. No rewrite needed.

## 7. UI Component Location

**Status:** FLAG -- path convention mismatch

The brief specifies:
```
sg_send_deploy__ui__admin/v0/v0.1/v0.1.2/deploy-vault-panel.js
```

The current UI structure is:
```
sg_send_deploy__ui__admin/v0/v0.1/v0.1.0/
  components/
    admin-shell/
    ec2-instances/
    ec2-key-pairs/
    ec2-security-groups/
    system-info/
  css/
  js/
```

**Issues:**
1. The brief puts the component in `v0.1.2/` but the current version is `v0.1.0/`. The versioned directory convention means creating a new version directory. This is intentional (each UI version gets its own directory), but it means `deploy__config.py` must be updated to point `UI__ADMIN__LATEST__VERSION` from `'v0.1.0'` to `'v0.1.2'`.
2. Existing components live in `v0.1.0/components/{component-name}/` as directories, not as standalone `.js` files in the version root. The brief puts `deploy-vault-panel.js` directly in `v0.1.2/`. It should follow the existing pattern: `v0.1.2/components/deploy-vault-panel/deploy-vault-panel.js`.
3. If we create `v0.1.2/`, we either need to copy all existing components from `v0.1.0/` or restructure the static file serving. This is a larger change than the brief implies.

**Recommendation:** Either:
- Add the component to the existing `v0.1.0/components/` directory (simpler, avoids version directory issues), or
- Create `v0.1.2/` as a full copy/evolution of `v0.1.0/` with the new component added (correct per versioning convention, but more work).

Clarify with Architect which approach to take.
