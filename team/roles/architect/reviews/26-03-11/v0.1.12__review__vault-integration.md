# Architect Review: Vault Integration for Deploy Service

**Version:** v0.1.12
**Date:** 2026-03-11
**Role:** Architect (Explorer Team)
**Brief under review:** `humans/dinis_cruz/briefs/03/11/v0.1.12__architect-brief__vault-integration.md`
**Reviewer:** Architect Agent

---

## Summary Assessment

**APPROVE WITH CONDITIONS**

The vault integration is architecturally sound and fills a genuine gap: the codebase currently hardcodes AMI IDs in `EC2__Defaults.py`, budget config defaults in `EC2_Budget_Config`, and security group IDs are passed as empty strings through constructors. The vault gives all of these a persistent, encrypted, auditable home.

The brief is well-structured, the dependency injection pattern matches the existing codebase, and the twin approach is consistent with the project's established testing philosophy. However, there are several conditions that must be addressed before or during implementation.

---

## 1. Architectural Fitness

**Assessment: Good fit.**

The brief proposes a clean dependency chain: `env vars -> Service__Vault -> config dicts -> service constructors`. This matches the existing pattern exactly. Today, `Fast_API__SG_Send__Deploy.setup()` already instantiates services with constructor injection:

```python
self.service_instances = Service__EC2_Instances()
self.llm_operation = Operation__EC2__Ephemeral__LLM(
    ec2_provider = self.service_instances.ec2_provider,
    audit_trail  = self.service_instances.audit_trail )
```

Adding `service_vault` as a field on the FastAPI app and passing vault-sourced config into `EC2_Budget_Config(**budget_data)` is a natural extension. No new architectural paradigm is introduced.

**One concern:** The brief shows `Service__Vault` using `Type_Safe` but with `_sync: object = None` as a private field. The existing `Service__EC2_Instances` and `Service__EC2_Budget` use plain `__init__` constructors, not `Type_Safe`. This inconsistency should be noted — `Service__Vault` would be the first service class to use `Type_Safe`. This is fine directionally (the CLAUDE.md says schemas use `Type_Safe`), but the developer should be aware that existing services may need migration later for consistency.

**Concern with `_sync` field:** The underscore-prefixed `_sync` field on a `Type_Safe` class may behave unexpectedly depending on how `Type_Safe` handles private attributes. The developer should verify this works or use a different mechanism (e.g., a `@property` with a cached backing attribute).

## 2. Interface Contracts

**Assessment: Clean and symmetric, with minor gaps.**

The `Service__Vault` and `Service__Vault__Twin` interfaces are well-aligned. Both implement the same 12 methods:

| Method | Service__Vault | Service__Vault__Twin |
|--------|---------------|---------------------|
| `setup()` | Reads env vars, creates temp dir | No-op, returns self |
| `is_configured()` | Checks vault_key | Returns `self.configured` |
| `can_write()` | Checks both keys | Returns configured AND write_enabled |
| `clone_or_pull()` | Network call | Returns empty diff |
| `read_file()` | Reads from disk | Reads from dict |
| `write_file()` | Writes to disk | Writes to dict |
| `push()` | Network call | Returns empty diff |
| `status()` | Network call | Returns clean status |
| `list_files()` | Walks filesystem | Returns sorted dict keys |
| `config_ec2()` | Convenience | Convenience |
| `config_budget()` | Convenience | Convenience |
| `config_stage()` | Convenience | Convenience |
| `state_fleet()` | Convenience | Convenience |
| `write_state_fleet()` | Convenience | Convenience |

**Missing from the interface:**

- **No formal protocol or ABC.** There is no shared base class or `typing.Protocol` to enforce that `Service__Vault` and `Service__Vault__Twin` stay in sync. If a method is added to one but not the other, tests will pass but production will break (or vice versa). Recommendation: define a `Protocol` class or at minimum add a unit test that asserts both classes have the same public method signatures.

- **No `read_file` error handling for malformed JSON.** `Service__Vault.read_file()` calls `json.load(f)` which will throw `json.JSONDecodeError` on corrupt files. The twin returns `{}` for missing paths but the real implementation will crash. Add a try/except that returns `{}` on parse failure, consistent with the degraded-mode philosophy.

- **`sync()` method is public on `Service__Vault` but absent from `Service__Vault__Twin`.** The `sync()` method returns the `Vault__Sync` instance. The twin has no equivalent. This is a minor gap since routes do not call `sync()` directly (they call `clone_or_pull()`, `push()`, `status()`), but any future code that accesses `service_vault.sync()` would break with the twin.

## 3. Startup Sequence

**Assessment: Risky as specified. Needs a timeout and error boundary.**

The brief specifies:

```python
if self.service_vault.is_configured():
    self.service_vault.clone_or_pull()   # sync on startup
```

This is called inside `Fast_API__SG_Send__Deploy.setup()`, which runs on every Lambda cold start.

**Concerns:**

1. **Cold-start latency.** `clone_or_pull()` performs a network round-trip to the vault server (clone = fetch tree + decrypt all files). If the vault has many files or the server is slow, this adds seconds to Lambda cold start. Lambda cold starts already include import time, VPC attachment (if any), and framework init. Adding a vault clone could push cold starts past acceptable thresholds. **Recommendation:** Measure this in integration tests. If > 500ms, consider lazy-loading (clone on first config read, not on startup).

2. **Network failure on startup.** If the vault server is unreachable during `clone_or_pull()`, the current code will throw an unhandled exception from `Vault__Sync.clone()`. This would crash the Lambda before it can serve any requests, violating the degraded-mode guarantee. **Requirement: Wrap `clone_or_pull()` in a try/except.** On failure, log the error and continue with empty config (degraded mode). The brief's prose says "does not crash" but the code does not enforce this.

3. **Temp directory lifecycle.** `tempfile.mkdtemp()` creates a directory in `/tmp`. On Lambda, `/tmp` persists across warm invocations but is limited to 512MB (or 10GB with ephemeral storage). The vault clone will accumulate across warm starts if `clone_or_pull()` creates new temp dirs. **The current code handles this correctly** (reuses `self.local_dir` and checks for `.sg_vault` to decide clone vs pull), but only if the `Service__Vault` instance itself is reused across invocations. Since `setup()` guards with `if self.service_vault is None`, warm invocations will reuse the same instance. This is correct.

4. **Race condition on pull.** If two concurrent Lambda invocations share the same warm container (they do not in AWS Lambda, but could in local dev), concurrent pulls to the same `local_dir` could corrupt state. Low risk in production but worth noting.

## 4. Degraded Mode

**Assessment: Partially specified. Needs tightening.**

The brief says: "If either env var is absent, the service starts and operates in degraded mode." The code supports this via `is_configured() -> False`, which causes `clone_or_pull()` to be skipped and `read_file()` to return `{}` (no files on disk).

**What works well:**

- `EC2_Budget_Config(**budget_data)` with `budget_data = {}` will create a default `EC2_Budget_Config` with `max_instances=5`, `daily_budget_usd=10.0`, `enforce_limits=False`. This is safe — defaults are permissive.
- Routes return `{}` or `[]` for unconfigured state, which is valid JSON.
- The `/vault/status` endpoint explicitly reports the degraded state.

**What needs attention:**

- **`enforce_limits` defaults to `False`.** This means degraded mode has no budget enforcement. This is the opposite of fail-safe. If the vault is unreachable, the system should arguably be MORE restrictive, not less. **Recommendation:** Change the default for `enforce_limits` in `EC2_Budget_Config` from `False` to `True`, or add explicit degraded-mode logic that enforces a conservative budget when vault is unavailable.

- **`ec2_config.get('security_group_id', '')` returns empty string when vault is unconfigured.** An empty `security_group_id` passed to `Operation__EC2__Ephemeral__LLM` means `_authorize_ingress()` silently skips SSH ingress scoping (because of the `if runner_ip and self.security_group_id:` guard). The instance would launch into the default VPC security group, which may have different rules. This is not a crash, but it is a silent security posture change. **Recommendation:** If `security_group_id` is empty and a launch is attempted, fail explicitly rather than launching with unknown security group configuration.

- **No monitoring/alerting hook for degraded mode.** When the service starts degraded, there is a startup warning log, but no structured alert. For a production system managing EC2 instances and spending real money, degraded mode should emit a CloudWatch metric or SNS notification. This can be deferred but should be tracked.

## 5. Security Posture

**Assessment: Acceptable for current phase, with caveats.**

**Vault key in env var:**
- Standard practice. AWS Lambda encrypts env vars at rest with KMS. The key never appears in logs (unless explicitly logged).
- The key format `<passphrase>:<vault_id>` (8 hex chars for vault_id) is passed as a single string. This is fine — `Vault__Crypto.derive_keys_from_vault_key()` handles parsing.

**Concerns:**

1. **Vault key in `Service__Vault.vault_key` field.** The vault key is stored as a plain `str` attribute on a `Type_Safe` object. If the object is ever serialized (`.json()`, `__repr__`, logging), the key will appear in plaintext. **Recommendation:** Override `__repr__` or use a property that masks the key. Alternatively, do not store the key on the object after setup — pass it to `clone_or_pull()` and discard.

2. **Access token scope.** The brief does not specify what the access token authorizes. If the token grants write access to the vault, and the vault holds config for production EC2 instances, then a compromised Lambda could modify budget limits, AMI IDs, or security group IDs. **Recommendation:** Document the blast radius of a compromised access token. Consider whether write access should be restricted to CI/CD only (not the running Lambda).

3. **No vault key rotation story.** The brief explicitly defers this, which is acceptable for v0.1.12, but the architecture should not make rotation impossible. Since the key is only read from env vars and passed to `Vault__Crypto`, rotation is a matter of updating the env var and redeploying. No architectural concern here.

4. **`read_file()` does path joining without sanitization.** `os.path.join(self.local_dir, relative_path)` with an attacker-controlled `relative_path` (e.g., `../../etc/passwd`) could read arbitrary files. The routes hardcode known paths (`config/ec2.json`, etc.), so this is not directly exploitable via the API, but if `read_file()` is ever exposed with user-supplied paths, it would be a path traversal vulnerability. **Recommendation:** Add path validation in `read_file()` — ensure the resolved path is within `self.local_dir`.

## 6. State Management

**Assessment: Dual-state risk. Needs clear ownership rules.**

The brief introduces `state/fleet.json` in the vault, which stores "last-known fleet snapshot." Meanwhile, the current system derives fleet state live from EC2 API calls (`Service__EC2_Instances.list_running()` calls `ec2_provider.list_instances()`).

**This creates two sources of truth:**

1. **EC2 API** (via `ec2_provider.list_instances()`) — always current, authoritative
2. **`state/fleet.json`** in the vault — a snapshot, potentially stale

**Questions the brief does not answer:**

- **When is `state/fleet.json` written?** The brief provides `write_state_fleet()` but does not specify when it is called. After every `create`/`terminate`? On a schedule? Manually via admin UI?
- **What is `state/fleet.json` used for?** If it is purely informational (admin dashboard), it is harmless. If any service reads it to make decisions (e.g., budget checks), it could allow stale data to bypass limits.
- **Conflict resolution.** If the vault fleet state says 2 instances running but EC2 API says 4, which wins? The brief does not specify.

**Recommendation:** Clearly document that `state/fleet.json` is a **cache/snapshot for observability only** and that all operational decisions (budget checks, instance limits) MUST use live EC2 API data. Add a comment to `write_state_fleet()` and `state_fleet()` stating this explicitly.

## 7. Scope Creep Risks

**Assessment: Scope is well-bounded, but two areas have hidden complexity.**

The brief explicitly defers per-room vaults, write-back UI, rotation, and secrets storage. The "not in scope" table is clear and comprehensive.

**Hidden complexity areas:**

1. **Admin UI component (`deploy-vault-panel`).** The brief specifies a Web Component with 7 panels, tab navigation, color-coded badges, and a sync button. This is a non-trivial frontend deliverable that will require its own testing and iteration. It is correctly scoped as read-only, but the effort estimate for the UI should not be underestimated. Consider whether the UI is blocking for the sprint goal (investor demo) or can be deferred.

2. **Stage config merging.** The brief shows `config/stages/dev.json` with override fields (`instance_type`, `security_group_id`, `spot_instance`). The wire-up section shows reading `config_ec2()` for base config but does not show how stage overrides are merged. The developer will need to implement a merge strategy (e.g., `{**base_config, **stage_config}`). This is straightforward but unspecified. **Recommendation:** Add a note to the brief or implementation guidance specifying the merge order and which fields are overridable.

3. **`sg-send-cli` version pinning.** The brief specifies `>= 0.5.3`. If `sg-send-cli` makes breaking changes to `Vault__Sync`, `Vault__API`, or `Vault__Crypto`, the deploy service breaks on next install. **Recommendation:** Pin to a compatible range (e.g., `>=0.5.3,<0.6.0`) or at minimum add an integration test that verifies the expected API surface.

## Risks and Mitigations

| # | Risk | Severity | Mitigation |
|---|------|----------|------------|
| R1 | `clone_or_pull()` network failure crashes Lambda on cold start | **High** | Wrap in try/except; continue in degraded mode |
| R2 | Degraded mode has `enforce_limits=False` — no budget safety net | **High** | Change default to `True` or add explicit degraded-mode enforcement |
| R3 | Empty `security_group_id` causes silent security posture change | **Medium** | Fail explicitly if SG ID is empty and a launch is attempted |
| R4 | `state/fleet.json` becomes second source of truth for fleet state | **Medium** | Document as observability-only; never use for operational decisions |
| R5 | Vault key exposed via `Type_Safe` serialization | **Medium** | Mask key in `__repr__`; do not store after initial use |
| R6 | Path traversal in `read_file()` if called with user input | **Low** | Validate resolved path stays within `local_dir` |
| R7 | Cold-start latency increase from vault clone | **Low** | Measure in integration test; consider lazy loading if > 500ms |
| R8 | No protocol/ABC enforcing twin interface parity | **Low** | Add interface parity test or `typing.Protocol` |

---

## Recommendations

### Must-fix before merge (conditions for approval)

1. **Wrap `clone_or_pull()` in try/except in `setup()`.** This is the single most critical fix. Without it, the degraded-mode guarantee is violated.

2. **Handle malformed JSON in `read_file()`.** Add try/except around `json.load()` returning `{}` on failure.

3. **Change `enforce_limits` default to `True`** in `EC2_Budget_Config`, or add explicit logic so that degraded mode (no vault) enforces conservative limits rather than permissive ones.

### Should-fix during implementation

4. **Add path validation to `read_file()`** to prevent path traversal.

5. **Document `state/fleet.json` as observability-only** in code comments and vault layout docs.

6. **Add an interface parity test** that asserts `Service__Vault` and `Service__Vault__Twin` have the same public method signatures.

7. **Specify stage config merge strategy** — document that stage overrides are shallow-merged over base EC2 config.

### Consider for follow-on

8. Vault key masking in serialization/logging.
9. Lazy-loading vault on first config read instead of on startup.
10. CloudWatch metric for degraded-mode startups.
11. Tighter version pinning for `sg-send-cli`.

---

## Conclusion

The vault integration is the right architectural move at the right time. It eliminates hardcoded config scattered across `EC2__Defaults.py` and constructor defaults, replaces it with an encrypted, versioned, auditable store, and does so with a clean dependency injection pattern that matches the existing codebase.

The primary risks are around startup resilience (R1, R2) and the potential for `state/fleet.json` to become a confusing second source of truth (R4). With the three must-fix conditions addressed, this brief is ready for implementation.
