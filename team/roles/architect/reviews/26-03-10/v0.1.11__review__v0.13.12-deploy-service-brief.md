### a) Assessment of the Brief

**Strengths**

1. **The "Deploy as appliance" recursion is elegant.** Making the Deploy Service follow the same ephemeral pattern it imposes on its children (LLM, Send Ephemeral) is a strong architectural choice. It means one pattern to learn, one pattern to secure, one pattern to monitor. The near-zero always-on cost ($5/month) is genuinely compelling for an investor demo and for real operations.

2. **Router Lambda as a stable entry point is the right boundary.** The separation between "stable DNS + routing" (Lambda, permanent, pennies) and "powerful compute with SSH" (EC2, ephemeral, dollars/hour) maps cleanly to the security model. Lambda never holds SSH keys or high-privilege IAM. The blast radius is bounded correctly.

3. **Vault-based state over SSM is well-argued.** Storing instance state in the SG/Send vault (zero-knowledge, portable, works locally) is consistent with the project philosophy and eliminates an AWS dependency for state management. The local-equivalence property is particularly valuable for the Type__Twins development loop.

4. **The async job model is necessary.** Stack creation taking 5-30 minutes makes synchronous HTTP impossible. POST returning 202 with a `job_id` and polling `/jobs/{id}` is the standard pattern and the right one.

5. **Five execution environments are well-defined.** The capability matrix is explicit about what works where. This is the kind of clarity that prevents "works on my machine" failures and avoids accidentally running expensive operations in the wrong context.

6. **The 3-phase build plan is correctly ordered.** Phase 1 (boot-on-demand + IP redirect) delivers demo value with the smallest scope. Phase 2 (DNS) is cosmetic but important for demo polish. Phase 3 (manage other appliances) is where the real product capability lives.

**Concerns and Risks**

1. **Cold start latency is a UX problem.** The brief acknowledges 60-90 seconds for EC2 boot. For a developer accessing `deploy.sgraph.ai`, waiting over a minute with a spinner every time the instance has gone idle is friction. If the idle timeout is 15 minutes and usage is sporadic, the cold start will happen frequently. The waiting page mitigates this for browser users, but API/CLI callers (CI pipelines, programmatic access) need a different pattern -- they need to be prepared to poll or block for 90 seconds before their first real request succeeds. The brief does not specify how the CLI handles this.

2. **Vault availability is a single point of failure.** If the SG/Send vault is unreachable, the Router Lambda cannot determine instance state, cannot write STARTING, and cannot function. The brief does not discuss vault failure modes or fallback behavior. At minimum, the Lambda should be able to fall back to `DescribeInstances` directly if vault reads fail.

3. **Two-mechanism shutdown has a consistency gap.** The heartbeat watcher writes `status=stopping` to vault and then runs `shutdown`. But between the vault write and the actual EC2 stop, there is a window where the vault says "stopping" but the instance is still running. If a new request arrives during this window, the Router Lambda sees "stopping" -- but the brief's state machine only shows RUNNING, STOPPED, and STARTING. What happens on a request when status=stopping? This state needs to be in the Router Lambda's state machine explicitly.

4. **The EC2 instance IP changes on every stop/start cycle.** Unless an Elastic IP is assigned (the brief calls this "optional, small cost"), the IP is different every boot. This means the vault state must be updated on every start, the waiting page must re-read the IP, and any cached DNS (even with 60s TTL) will be stale for the first minute after boot. For Phase 1 (raw IP redirect), this is particularly visible. The brief should state whether Elastic IP is recommended for the Deploy appliance specifically.

5. **The brief describes creating IAM roles for child appliances, but CLAUDE.md Rule 10 says "No IAM role" for EC2 instances.** The brief says "each appliance gets its own minimal-privilege IAM role" and the stack lifecycle includes "Create IAM role (boto3, minimal permissions)." This contradicts the current security posture documented in CLAUDE.md. The brief appears to be superseding this rule, but this should be explicit.

6. **Type__Twins vision is ambitious but the brief conflates current state with future vision.** The fractal chain, security review workflow, and state inspection superpower described in the brief are not things that exist today. The current `Type__Twin__EC2__Instance` is a simple in-memory mock with hardcoded IPs. The brief reads as though the persisted Twin, call logging, and replay capability are near-term deliverables, but they are substantial pieces of infrastructure in their own right. The gap between what exists and what is described needs to be acknowledged in the implementation plan.

7. **No mention of how the Deploy EC2 gets its AMI ID on first boot.** The Router Lambda needs to know which AMI to start (or which instance to `StartInstances`). The brief says "Lambda reads vault" for the instance ID, but on very first deployment, there is no vault entry and no pre-existing instance. The bootstrap/first-run sequence is not specified.

**Gaps and Ambiguities**

- **Health check endpoint on the Deploy EC2:** The brief references health pings but does not specify the path. Is it `/health`, `/info/health`, or `/status`? The current codebase uses `Routes__Info` which likely provides `/info/health`.
- **Vault client implementation:** There is no vault client anywhere in the current codebase. The brief assumes it exists. Is this provided by osbot-utils, by the SG/Send app, or does it need to be built?
- **EventBridge watchdog Lambda:** Is this a separate Lambda function, a separate handler in the same Lambda, or a scheduled invocation of the Router Lambda with a different event shape?
- **Port:** The brief says `http://{ip}:8080` but the current CLAUDE.md says port 443 inbound only. Which is it for the Deploy appliance?
- **TLS for Phase 1:** With raw IP redirect to port 8080, there is no TLS. The brief acknowledges this is addressed in Phase 2 with ACM wildcard, but Phase 1 has the Deploy API exposed over plain HTTP. This has security implications for the access token.

### b) Delta from Current Architecture

**Topology Change: The Fundamental Shift**

```
CURRENT ARCHITECTURE (v0.1.11)
    Lambda (full Deploy Service FastAPI + Mangum)
        → EC2 instances (data rooms, managed by Lambda)

BRIEF'S ARCHITECTURE (v0.13.12)
    Router Lambda (thin: start/stop/redirect only)
        → Deploy EC2 (full Deploy Service FastAPI)
            → Child EC2 instances (LLM, Send, etc., managed by Deploy EC2 via SSH)
```

The Lambda goes from being the brain to being a traffic light. The brain moves to EC2.

**EC2_Provider vs Type__Twins**

The current `EC2_Provider` abstraction (at `/home/user/SG_Send__Deploy/sg_send_deploy/ec2/providers/EC2_Provider.py`) is a classic strategy pattern: an interface with two implementations (AWS and Twin). The brief's Type__Twins model is different -- it is a transparent boundary that auto-selects based on credential availability. The key differences:

- **Current:** Caller explicitly chooses `EC2_Provider__AWS()` or `EC2_Provider__Twin()` at construction time.
- **Brief:** A single `Type__Twin__EC2` that detects credentials and routes accordingly. No caller choice needed.

The migration path: keep the `Type__Twin__EC2__Instance` and `Type__Twin__EC2__Fleet` classes as the no-creds implementation, add credential detection to `Type__Twin`, and make the real-AWS path a delegate inside the Twin rather than a separate provider. The `EC2_Provider` interface can be retired.

**Operation__EC2__Ephemeral__LLM vs Async Job Model**

The current `Operation__EC2__Ephemeral__LLM` (at `/home/user/SG_Send__Deploy/sg_send_deploy/workflows/actions/Operation__EC2__Ephemeral__LLM.py`) is a synchronous, single-threaded orchestrator: it launches EC2, opens an SSH tunnel, runs Ollama checks, and cleans up -- all in one blocking `execute()` call. The brief's model is fundamentally different:

- **Current:** Synchronous. Caller blocks until completion. Uses SSH port forwarding from the Lambda/caller to the instance.
- **Brief:** Asynchronous. POST returns `job_id` immediately. A background worker (asyncio task or thread) executes the steps. The caller polls `/jobs/{id}`. SSH runs directly from the Deploy EC2, not through tunnels.

The LLM operation's step sequence (create key pair, authorize ingress, launch, wait, verify, invoke, cleanup) maps well to a list of named steps in a job. The refactor is: extract the step list from `Operation__EC2__Ephemeral__LLM.execute()`, wrap each step in a `Job__Step`, and execute them in a background task with progress tracking.

**Docker Lambda Image**

The current Dockerfile at `/home/user/SG_Send__Deploy/sg_send_deploy/docker/images/sg_send_deploy/Dockerfile` is a Lambda container image (`FROM public.ecr.aws/lambda/python:3.12-arm64`). Per the brief, the Router Lambda is thin enough for a zip deployment -- it only needs boto3 (already in the Lambda runtime) and the vault client. The Docker Lambda image is not needed for the deployed Lambda.

However, the Docker image concept is needed for:
1. **Docker Hub distribution** (`sgraph/sg-deploy`) -- a CLI/server image, not a Lambda image.
2. **Local development** -- running the full Deploy Service locally.

The `Lambda_Docker__SG_Send__Deploy` class and the Dockerfile both need to be repurposed from "Lambda container" to "CLI/server container."

**What to Build First for Fastest Demo Value**

Phase 0 + Phase 1 together deliver the "boot-on-demand" demo in under a week: hit a URL, see a waiting page, get redirected to the running Deploy Service. This is the single most impressive demo moment -- "it costs nothing when nobody is using it, and it appears in 60 seconds when someone does."

Phase 2 (Deploy EC2 FastAPI) can proceed in parallel with Phase 1 since they share only the vault client dependency. Once both are done, Phase 3 wires them together.

The brief is architecturally sound and represents the right evolution of this system. The primary execution risk is the breadth of new infrastructure required (vault client, job model, Router Lambda, AMI baking, auto-shutdown) versus the existing codebase, which is relatively small. Roughly 60% of the current code will be retired or heavily refactored; only the schemas, budget service, audit entry, and twin core survive intact.
