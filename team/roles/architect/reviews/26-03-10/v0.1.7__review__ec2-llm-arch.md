# Architect Review: Ephemeral EC2 LLM Architecture

**Version:** v0.1.7
**Date:** 2026-03-10
**Role:** Architect (Explorer Team)
**Brief Under Review:** `humans/dinis_cruz/briefs/03/10/v0.1.5__ec2_llm_arch.md`

---

## Executive Summary

The brief proposes ephemeral EC2 instances with Ollama-powered LLM inference via SSH tunneling for CI-driven QA checks. The pattern is **architecturally sound and fits well with existing patterns**.

**Alignment verdict:** Strong fit with existing architecture
**Key finding:** This is a *lateral expansion*, not a *new abstraction*. It introduces a new Operation class alongside existing services, composes existing twins and providers, and requires only one small extension to `SSH__Execute` (port forwarding).

**Recommendation:** Proceed as planned. All five phases are feasible. Blockers are minimal and well-scoped.

---

## 1. Alignment with Existing Architecture

### 1.1 Provider Abstraction Pattern

The brief uses osbot-aws classes (`EC2`, `EC2_Instance`, `SSH`, `SSH__Execute`) directly rather than routing through `EC2_Provider`. This is appropriate because:

- The operation is **ephemeral and procedural** (launch -> verify -> invoke -> cleanup), not persistent state management
- It doesn't participate in the data room fleet lifecycle (which uses `EC2_Provider`)
- It follows the pattern of other procedural operations like the Mitmproxy reference implementation

**Decision:** The LLM operation lives **outside the provider abstraction** as a standalone `Operation__EC2__Ephemeral__LLM` class.

### 1.2 Type_Safe Schemas

All proposed schemas use Type_Safe, not Pydantic. Compliant with CLAUDE.md rule 1.

- `Schema__QA__Check` -- individual QA check definition
- `Schema__QA__Result` -- result of running a check
- `Schema__Request__EC2__LLM__Execute` and `Schema__Response__EC2__LLM__Execute` -- API request/response

### 1.3 Twin/Surrogate Pattern

The proposed `Ollama__Surrogate` follows the established twin pattern:

- Consistent with `Type__Twin__EC2__Instance` and `Type__Twin__EC2__Fleet`
- Maintains the "no mocks, no patches" testing rule (CLAUDE.md 21)
- Provides a real object with real state; only the external boundary (Ollama HTTP API) is replaced

**Recommendation:** Rename to `Type__Twin__Ollama` for naming consistency, or keep as `Ollama__Surrogate` if the team prefers to distinguish non-AWS twins.

### 1.4 Budget Controls -- Implicit but Required

The brief does not explicitly mention budget checks before instance launch. The operation **must** call `Service__EC2_Budget.check_instance_limit()` before launching. Add to the execution flow:

```
1.5 Check budget constraint
    budget_check = self.budget_service.check_instance_limit(len(running))
    if not budget_check['allowed']:
        raise CIBudgetExceededError(budget_check['message'])
```

### 1.5 Audit Trail -- Implicit but Required

The brief logs errors but does not mention audit trail recording. The Operation class should record each workflow execution:

```python
self.audit_trail.record(
    action  = 'LLM_EXECUTE_WORKFLOW'  ,
    admin   = admin_id                 ,
    details = dict(workflow_id=run_id, instance_id=instance_id, ...))
```

## 2. API Contract Analysis

### 2.1 Route Location

The brief proposes `POST /workflows/execute`. Current routes are under `/ec2/instances` (CRUD).

**Recommendation:** New `Routes__EC2_Workflows` router, mounted at `/ec2/workflows/execute`.

Rationale:
- Workflows are a new concern, distinct from instance CRUD
- Separates procedural operations from state management
- Allows different auth requirements later
- Route stays thin (2 lines of logic), business logic in Operation class

```python
class Routes__EC2_Workflows(Fast_API__Routes):
    tag = 'ec2-workflows'

    def workflows__execute(self,
                          request: Schema__Request__EC2__LLM__Execute
                          ) -> Schema__Response__EC2__LLM__Execute:
        operation = Operation__EC2__Ephemeral__LLM(
            request        = request        ,
            audit_trail    = self.audit_trail,
            budget_service = self.budget_service)
        return operation.execute()
```

### 2.2 Request/Response Schemas

Both schemas are well-structured. Request validates at construction time via Type_Safe. Response includes all necessary fields for CI pipeline consumption (success, metrics, results, error).

## 3. State Machine: Ephemeral vs Persistent Lifecycle

### No Conflict

**Data room lifecycle** (persistent):
```
NO_INSTANCE -> BOOTING -> RUNNING_VANILLA -> READY -> ACTIVE -> SHUTTING_DOWN -> NO_INSTANCE
```

**LLM workflow lifecycle** (ephemeral):
```
create -> wait_for_ssh -> open_tunnel -> batch_invoke -> cleanup (finally)
```

These are **orthogonal**:
- Different EC2 instances (LLM ephemeral vs data room long-lived)
- Different state management (synchronous operation vs persistent fleet state)
- Shared budget limit (both count against the 5-instance cap)
- No resource conflicts

The `finally` block is the critical invariant: every resource (key pair, SG rule, instance) is cleaned up regardless of which exception was raised.

## 4. Security Posture Assessment

The brief's security model is strong:

- **Ollama confinement:** Binds to `127.0.0.1:11434` only, SSH tunnel provides access
- **Ephemeral credentials:** Key pair generated per run, deleted in finally block
- **Blast radius:** Instance auto-terminates in finally block, SG rule scoped to runner IP
- **No egress:** Matches CLAUDE.md rule 9

Matches the security posture established in the project. No concerns.

**Note:** The Architect assessment differs from the Developer assessment on blocker severity. The Developer identified a HIGH blocker around Lambda's lack of an `ssh` binary for tunneling. The Architect considers this a design detail resolvable in Phase 1 (use paramiko `Transport.open_channel()` instead of subprocess). See Developer review for implementation-level blockers.
