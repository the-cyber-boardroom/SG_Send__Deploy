## Executive Summary

The Type__Twin concept brief proposes "alive" digital twins of AWS services using the three-layer hierarchy: `Schema__Twin__Config` (static configuration), `Schema__Twin__State` (runtime state), and `Type__Twin` (alive simulation with `execute()`). While the brief focuses on CloudFront log pipelines, the pattern applies directly to SG_Send__Deploy's core problem: managing EC2 instances, security groups, and DNS for ephemeral data rooms.

This review maps the Type__Twin architecture onto our specific domain and identifies the concrete twins we need, how they compose, where they fit in the codebase, and which to build first for maximum impact on testability.

**Key finding:** Type__Twin solves our most urgent architectural gap. Today, `Service__EC2_Instances` imports `osbot_aws.aws.ec2.EC2` inside every method with lazy imports, making it impossible to unit-test without hitting real AWS. A `Type__Twin__AWS__EC2` replaces this with an in-memory simulation that honours our "no mocks, no patches" rule while enabling fast, deterministic testing of the full boot sequence state machine.

## 1. How Type__Twin Applies to SG_Send__Deploy

SG_Send__Deploy manages four categories of AWS resources:

| Resource | Current Code | AWS API Surface | Twin Needed? |
|----------|-------------|-----------------|:---:|
| **EC2 Instances** | `Service__EC2_Instances` | create, start, stop, terminate, describe | Yes (Phase 0) |
| **Security Groups** | Not yet implemented | create, authorize ingress/egress, describe | Yes (Phase 1) |
| **AMIs** | Placeholder (`ami/`) | describe, create, deregister | Yes (Phase 1) |
| **DNS (Route 53)** | Not yet implemented | change resource record sets | Yes (Phase 2) |
| **Key Pairs** | Referenced in schemas | create, describe, delete | Optional |
| **VPC / Subnets** | Not yet implemented | describe (read-only for us) | Optional |

The concept brief's pipeline composition pattern (CloudFront -> Firehose -> S3 -> Lambda) maps to our orchestration chain:

```
EC2 Twin (create instance)
    -> Security Group Twin (attach rules)
        -> AMI Twin (resolve image)
            -> DNS Twin (create record)
                = Running Data Room
```

Each step in the data room boot sequence is a typed transformation. The output of one step feeds the next. Type__Twin makes this chain testable without AWS.

## 2. The EC2 Twin Architecture

### Type__Twin__AWS__EC2__Instance

This is the centrepiece twin for SG_Send__Deploy. It simulates the EC2 instance lifecycle that AWS exposes through the `describe-instances` API.

#### State Transitions

The twin must enforce the same state transitions that AWS enforces. An instance in `stopped` state cannot be terminated directly without going through `shutting-down` first. The twin rejects illegal transitions:

```
                 +-----------+
                 |  pending  |
                 +-----+-----+
                       |
                       v
                 +-----------+
          +----->|  running  |<-----+
          |      +-----+-----+     |
          |        |       |       |
          |        v       v       |
     +----+----+        +----+----+
     | starting|        | stopping|
     +---------+        +----+----+
          ^                  |
          |                  v
          |           +-----------+
          +-----------+  stopped  |
                      +-----+-----+
                            |
                            v
                   +--------------+
                   |shutting-down |
                   +------+-------+
                          |
                          v
                   +--------------+
                   | terminated   |
                   +--------------+
```

**Legal transitions table:**

| From State | Allowed Actions | To State |
|-----------|----------------|----------|
| `(none)` | create / run | `pending` |
| `pending` | (automatic) | `running` |
| `running` | stop | `stopping` |
| `running` | terminate | `shutting-down` |
| `stopping` | (automatic) | `stopped` |
| `stopped` | start | `pending` |
| `stopped` | terminate | `shutting-down` |
| `shutting-down` | (automatic) | `terminated` |
| `terminated` | (none) | terminal state |

The twin's `execute()` method checks the current state, validates the requested transition, and either applies it or returns an error -- exactly as the real EC2 API would.

#### Instance ID Generation

The twin generates deterministic instance IDs for testability:


#### IP Address Simulation

- **Private IP:** Assigned from a simulated subnet CIDR range on creation. Persists through stop/start cycles.
- **Public IP:** Assigned on `running` state entry (unless in a VPC with no public IP assignment). Cleared on `stopping`.

This matters because our `EC2_Instance_Info` schema captures both `public_ip` and `private_ip`, and the fleet management logic needs these to route SSH commands.

## 3. Schema Mapping: Three Layers Applied to Our Domain

### EC2 Domain

| Layer | Class | Maps to Existing |
|-------|-------|-----------------|
| Config | `Schema__Twin__Config__AWS__EC2__Instance` | Fields from `EC2_Instance_Info` that are set at creation time (`instance_type`, `ami_id`, `key_name`) |
| State | `Schema__Twin__State__AWS__EC2__Instance` | Fields from `EC2_Instance_Info` that change at runtime (`status`, `public_ip`, `uptime_seconds`) |
| Twin | `Type__Twin__AWS__EC2__Instance` | Replaces the lazy `from osbot_aws.aws.ec2.EC2 import EC2` inside `Service__EC2_Instances` |

### Security Group Domain

| Layer | Class | Purpose |
|-------|-------|---------|
| Config | `Schema__Twin__Config__AWS__EC2__Security_Group` | Group ID, VPC ID, ingress/egress rules |
| State | `Schema__Twin__State__AWS__EC2__Security_Group` | Attached instance count, rule evaluation cache |
| Twin | `Type__Twin__AWS__EC2__Security_Group` | Simulates `authorize_ingress`, `authorize_egress`, rule evaluation |

The security posture rules from CLAUDE.md (port 443 inbound only, zero egress, no IAM role) become **assertions on the twin's config**:

```python
# In tests — the twin config IS the security posture
sg_config = Schema__Twin__Config__AWS__EC2__Security_Group(
    ingress_rules = [Schema__SG__Rule(port=443, protocol='tcp', cidr='0.0.0.0/0')],
    egress_rules  = []                                                              )

# Assert the security posture is correct by construction
assert len(sg_config.ingress_rules) == 1
assert sg_config.ingress_rules[0].port == 443
assert len(sg_config.egress_rules) == 0
```

### AMI Domain

| Layer | Class | Purpose |
|-------|-------|---------|
| Config | `Schema__Twin__Config__AWS__EC2__AMI` | AMI ID, architecture (arm64), root device, creation date |
| State | `Schema__Twin__State__AWS__EC2__AMI` | Available/pending/deregistered status |
| Twin | `Type__Twin__AWS__EC2__AMI` | Simulates `describe_images`, AMI lifecycle |

### DNS Domain (Route 53)

| Layer | Class | Purpose |
|-------|-------|---------|
| Config | `Schema__Twin__Config__AWS__Route53__Zone` | Hosted zone ID, domain (`send.sgraph.ai`) |
| State | `Schema__Twin__State__AWS__Route53__Zone` | Current record sets, record count |
| Twin | `Type__Twin__AWS__Route53` | Simulates `change_resource_record_sets` for `{room-name}.send.sgraph.ai` |

### Fleet / Data Room Domain (Application Layer)

The fleet layer is an **application-level twin**, not an AWS twin. It composes the AWS twins:

| Layer | Class | Purpose |
|-------|-------|---------|
| Config | `Schema__Fleet__Room__Config` | Room name, branding, documents, TTL |
| State | `Schema__Fleet__Room__State` | Boot sequence state (the 7-state machine), assigned instance ID, DNS record |
| Twin | `Type__Twin__Fleet__Room` | Orchestrates the boot sequence by calling EC2 + SG + DNS twins |

This is the composition layer where our domain logic lives, distinct from the AWS simulation layer.

### Audit Domain

The audit trail does not need a twin -- it already works in-memory. The `Audit_Trail` class with its hash-chained `EC2_Audit_Entry` objects is already an in-memory implementation that follows the same principle as twins: no external dependency, deterministic behaviour. It stays as-is but integrates with twins by recording twin operations the same way it records real operations.

## 4. Composition: How Twins Work Together

### The Data Room Boot Sequence as a Twin Pipeline

The data room boot sequence (from CLAUDE.md: `NO_INSTANCE -> BOOTING -> RUNNING_VANILLA -> READY -> ACTIVE -> SHUTTING_DOWN -> NO_INSTANCE`) maps to a composed chain of twin operations:

```
Step 1: EC2 Twin.execute(create)     -> instance in 'pending' state
Step 2: EC2 Twin.execute(wait_run)   -> instance in 'running' state, IP assigned
Step 3: SG Twin.execute(attach)      -> security group attached
Step 4: DNS Twin.execute(create_A)   -> A record pointing to instance IP
Step 5: SSH Twin.execute(push_config)-> config pushed to instance
Step 6: HTTP Twin.execute(health)    -> health check passes
```

Each step produces a typed output that feeds the next step's input. Type_Safe catches schema mismatches at construction time, not at runtime in production.

### Type__Twin__Fleet__Environment

The fleet environment wires all twins together, analogous to `AWS__Twin__Environment` from the concept brief:


**Key design choice:** `Service__EC2_Budget` and `Audit_Trail` are **not twinned**. They already work in-memory with no AWS dependency. They are real implementations composed alongside twins. This is the pragmatic approach -- only twin what has an external dependency.

### Integration Point: Service__EC2_Instances

The critical integration point is `Service__EC2_Instances`. Today it does lazy imports of `osbot_aws.aws.ec2.EC2` inside every method. With twins, it receives an EC2 interface through dependency injection:

```python
# Current (untestable without AWS):
class Service__EC2_Instances:
    def __init__(self, budget_service=None, audit_trail=None):
        self.budget_service = budget_service or Service__EC2_Budget()
        self.audit_trail    = audit_trail    or Audit_Trail()

    def create(self, ...):
        from osbot_aws.aws.ec2.EC2 import EC2     # <-- hidden dependency
        ec2 = EC2()
        result = ec2.instance_create(...)

# With twins (testable):
class Service__EC2_Instances:
    def __init__(self, ec2_provider=None, budget_service=None, audit_trail=None):
        self.ec2_provider   = ec2_provider   or self._default_ec2()
        self.budget_service = budget_service or Service__EC2_Budget()
        self.audit_trail    = audit_trail    or Audit_Trail()

    def _default_ec2(self):
        from osbot_aws.aws.ec2.EC2 import EC2
        return EC2()

    def create(self, ...):
        result = self.ec2_provider.instance_create(...)    # <-- uses whatever was injected
```

The twin implements the same interface as `osbot_aws.aws.ec2.EC2`:

```python
class Type__Twin__AWS__EC2(Type__Twin__AWS):
    # Implements the same methods as osbot_aws EC2:
    def instance_create(self, image_id, instance_type, key_name, **kwargs):
        ...
    def instances_details(self):
        ...
    def instance_details(self, instance_id):
        ...
    def instance_terminate(self, instance_id):
        ...
    def instance_stop(self, instance_id):
        ...
    def instance_start(self, instance_id):
        ...
```

This is the `AWS__Twin__*__Boto3` pattern from the concept brief, adapted for `osbot-aws` instead of raw boto3. The twin provides the same method signatures as the osbot-aws `EC2` class.

### No Changes to Routes

Routes remain thin wrappers (per CLAUDE.md rule 7). They call `Service__EC2_Instances` the same way regardless of whether the service uses a real EC2 backend or a twin. The twin is invisible at the route layer.

## 6. Testing Strategy: No Mocks, No Patches

### Current Testing Gap

The existing test suite covers:
- `Service__EC2_Budget` -- fully tested (no AWS dependency)
- `Audit_Trail` -- fully tested (no AWS dependency)
- `EC2_Instance_Info`, `EC2_Budget_Config`, `EC2_Audit_Entry` -- schemas tested
- `Service__EC2_Instances` -- **NOT TESTED** (requires real AWS)
- `Routes__EC2_Instances` -- **NOT TESTED** (requires real AWS through service)
- `Deploy__Fast_API` -- **NOT TESTED** (requires real AWS through routes)

This is the gap the twins close. The entire service and route layer is untestable today without AWS credentials.

### Testing with Twins

```python
class Test__Service__EC2_Instances(TestCase):

    @classmethod
    def setUpClass(cls):
        # Create a twin EC2 environment — no AWS, no mocks
        cls.ec2_twin     = Type__Twin__AWS__EC2()

        cls.audit        = Audit_Trail()
        cls.service      = Service__EC2_Instances(
                               ec2_provider   = cls.ec2_twin ,
                               budget_service = cls.budget   ,
                               audit_trail    = cls.audit    )

    def test_create__success(self):
        result = self.service.create(
            instance_type = 't3.micro'                   ,
            data_room_id  = 'room-demo'                  ,
            image_id      = 'ami-test123'                ,
            key_name      = 'deploy-key'                 ,
            admin         = 'test-admin'                 )

        assert result['status']      == 'created'
        assert result['instance_id'] != ''               # Twin generated a valid ID
        assert result['instance_type'] == 't3.micro'

    def test_create__budget_limit_reached(self):
        # Pre-populate the twin with 3 running instances
        for i in range(3):
            self.ec2_twin.instance_create(
                image_id      = f'ami-{i}'               ,
                instance_type = 't3.micro'               ,
                key_name      = 'key'                    )

        result = self.service.create(
            instance_type = 't3.micro'                   ,
            admin         = 'test-admin'                 )

        assert result['status']  == 'error'
        assert 'limit reached' in result['message']

    def test_create__audit_trail_recorded(self):
        result = self.service.create(
            instance_type = 't3.micro'                   ,
            image_id      = 'ami-test'                   ,
            admin         = 'admin-1'                    )

        entries = self.audit.get_entries()
        last    = entries[-1]
        assert last.action == 'EC2_CREATE'
        assert last.admin  == 'admin-1'

    def test_terminate__transitions_state(self):
        # Create an instance via twin
        create_result = self.ec2_twin.instance_create(
            image_id='ami-test', instance_type='t3.micro', key_name='key')
        instance_id = create_result['instance_id']

        # Terminate it
        result = self.service.terminate(instance_id=instance_id, admin='admin-1')
        assert result['status'] == 'terminated'

        # Verify the twin's state changed
        details = self.ec2_twin.instance_details(instance_id=instance_id)
```

## 7. State Machine Alignment

### The Data Room Boot Sequence

CLAUDE.md defines the 7-state boot sequence:

```
NO_INSTANCE -> BOOTING -> RUNNING_VANILLA -> READY -> ACTIVE -> SHUTTING_DOWN -> NO_INSTANCE
```

This is a **data room** state machine (application level), not an EC2 state machine (AWS level). The two state machines run in parallel:

| Data Room State | EC2 Instance State | What Just Happened |
|----------------|-------------------|-------------------|
| `NO_INSTANCE` | `(none)` | No instance exists for this room |
| `BOOTING` | `pending` | `run_instances` called, instance launching |
| `RUNNING_VANILLA` | `running` | Instance booted, OS is up, SG/Send not configured |
| `READY` | `running` | Config pushed via SSH/admin API, SG/Send responding |
| `ACTIVE` | `running` | DNS record created, room accessible at `{name}.send.sgraph.ai` |
| `SHUTTING_DOWN` | `stopping` / `shutting-down` | Shutdown initiated, data synced |
| `NO_INSTANCE` | `terminated` / `stopped` | Instance cleaned up, DNS removed |

### How Twins Model This

The **EC2 twin** handles the AWS-level state machine (pending -> running -> stopping -> stopped -> shutting-down -> terminated). The **Fleet twin** handles the data room state machine and orchestrates the EC2 twin transitions:

```python
class Type__Twin__Fleet__Room(Type_Safe):
    room_state : str = 'NO_INSTANCE'                   # Data room state
    ec2_twin   : Type__Twin__AWS__EC2__Instance = None  # The underlying instance twin
    dns_twin   : Type__Twin__AWS__Route53       = None  # DNS management

    def boot(self, config: Schema__Fleet__Room__Config) -> str:
        # NO_INSTANCE -> BOOTING
        self.room_state = 'BOOTING'
        self.ec2_twin = Type__Twin__AWS__EC2__Instance(config=...)
        self.ec2_twin.execute(action='run')             # EC2: (none) -> pending

        # BOOTING -> RUNNING_VANILLA
        self.ec2_twin.execute(action='wait_running')    # EC2: pending -> running
        self.room_state = 'RUNNING_VANILLA'

        # RUNNING_VANILLA -> READY
        # (push config would happen here via SSH twin)
        self.room_state = 'READY'

        # READY -> ACTIVE
        self.dns_twin.execute(action='create_record',
                              name=f'{config.room_name}.send.sgraph.ai',
                              ip=self.ec2_twin.state.public_ip)
        self.room_state = 'ACTIVE'

        return self.room_state
```

### Failure Paths

The twin must model failure at every transition:

| Failure Point | Data Room Result | EC2 State |
|--------------|-----------------|-----------|
| Instance fails to launch | `BOOTING` -> `NO_INSTANCE` | `pending` -> `terminated` (AWS auto) |
| Instance boots but SSH fails | `RUNNING_VANILLA` (stuck) | `running` |
| Config push fails | `RUNNING_VANILLA` (stuck) | `running` |
| Health check fails after config | `READY` (stuck, retry) | `running` |
| DNS creation fails | `READY` (stuck, retry) | `running` |
| Idle timeout triggers | `ACTIVE` -> `SHUTTING_DOWN` | `running` -> `stopping` |

The 30-minute idle auto-terminate (CLAUDE.md rule 15) is modelled by the fleet twin's timer logic, not the EC2 twin. The EC2 twin doesn't know about idle timeouts -- that's application-level policy.

## Architectural Observations

### 1. The Current Code Has the Right Seams

`Service__EC2_Instances` already takes `budget_service` and `audit_trail` as constructor parameters. Adding `ec2_provider` follows the same pattern. The refactoring is minimal -- the architecture was headed this direction anyway.

### 2. EC2_Audit_Entry Should Become Type_Safe

The existing `EC2_Audit_Entry` class uses plain Python `__init__` rather than inheriting from `Type_Safe`. This is the only schema that doesn't use `Type_Safe`. It should be migrated for consistency and to gain `.json()` / `.from_json()` round-trip serialisation. This is a prerequisite for storing audit trails in Memory-FS (CLAUDE.md rule 20).

### 3. Twins Are Not Mocks

The concept brief is explicit: twins are **simulations**, not mocks. A mock returns whatever you tell it to. A twin enforces state transitions and rejects illegal operations. When you call `terminate` on an instance that's already terminated, the twin returns an error -- the same error AWS would return. This is why twins satisfy the "no mocks, no patches" rule: they are real implementations of the AWS behaviour contract, backed by in-memory state.

### 4. 100% Fidelity for Supported Surface Area

Per the concept brief's resolved decision 5: every `Type__Twin__AWS__*` class must match real AWS exactly, including quirks. For EC2, this means:
- Instance state transitions follow the exact AWS state machine
- `describe_instances` returns the same dict structure as osbot-aws
- Terminating a stopped instance goes through `shutting-down` first
- You cannot start a `pending` instance

The twin does NOT need to simulate things we don't use (placement groups, spot instances, elastic GPUs). Organic scope applies -- only implement what we call.

### 5. Config as Infrastructure Definition

Per the concept brief's resolved decision 3: twin configs stored in the repo represent "what does our AWS environment look like." For SG_Send__Deploy, this means we store the actual EC2 configs (instance types, AMI IDs, security group rules, VPC details) as `Schema__Twin__Config__AWS__*` JSON files. These configs serve double duty:
- **Testing:** Feed them to twins for realistic simulation
- **Documentation:** They are the living, executable specification of our infrastructure
