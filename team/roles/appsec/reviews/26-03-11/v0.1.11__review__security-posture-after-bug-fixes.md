# AppSec Review: Security Posture After Bug Fixes

**Version:** v0.1.11
**Date:** 2026-03-11
**Role:** AppSec

---

## Summary

Reviewed all bug fixes for security implications. No new vulnerabilities introduced. One pre-existing concern noted.

## Findings

### 1. security_group_authorize_ingress — Was Silently Failing (GOOD)

The wrong parameter name (`group_id` instead of `security_group_id`) meant this method **never worked**. This is actually a security-positive outcome — no ingress rules were accidentally created. Now that it's fixed, any call to this method will actually open ports. Verify that:
- Only port 443 is ever passed
- CIDR ranges are tightly scoped
- Calls are audit-logged

### 2. security_group_revoke_ingress — Uses boto3 Directly

`EC2_Provider__AWS.security_group_revoke_ingress()` calls `ec2.client().revoke_security_group_ingress()` directly. This bypasses osbot-aws and violates the project rule "never use boto3 directly". While functionally fine, it means this call isn't subject to any osbot-aws guardrails.

**Recommendation:** Check if osbot-aws has a `security_group_revoke_ingress` method. If not, this is acceptable as a temporary measure but should be tracked.

### 3. Admin UI — No Authentication

The admin UI at the root path has no authentication. For demo purposes this is acceptable if the Lambda is behind API Gateway with IAM auth or a VPN. For production, the UI needs auth.

### 4. SSH Key Path — Now Correct

The `key_pair_create` fix means SSH private keys will now be written to the correct path (`/tmp/{key_name}.pem`). Verify that:
- Lambda's `/tmp` is ephemeral (it is — Lambda clears between cold starts)
- Keys are not logged or returned in API responses
- Keys are used immediately then discarded

## Verdict

No new security issues introduced. The fixes improve correctness without expanding attack surface.
